# ImageCompressor

Пакетное сжатие семейного фото/видео архива: **фото/анимация → AVIF**, **видео → MP4 + AV1**,
**визуально без потерь**, с **сохранением метаданных и времени файлов**, **идемпотентно**
(повторный запуск не трогает готовое) и **отказоустойчиво** (падение посреди прогона не портит
данные). Один самодостаточный exe — кодеки вшиты внутрь.

Вся внутренняя текстовка программы (интерфейс, ошибки, журнал) — на английском: консоли с
разными кодовыми страницами не ломаются, журнал остаётся грепабельным.

---

## Как пользоваться (основной сценарий)

1. Скопируй `image_compressor.exe` в корень архива.
2. Запусти его — **без аргументов**. Он сожмёт свою папку рекурсивно прямо на месте:

   ```powershell
   cd C:\FData
   .\image_compressor.exe
   ```

3. Подтверди один раз (`y`). Дальше работает живая строка статуса; лог изменений пишется
   в `image_compressor.log` рядом с БД.
4. Если идёшь за компьютером параллельно с прогоном — сразу после старта во втором окне:

   ```powershell
   Get-Process image_compressor | ForEach-Object { $_.PriorityClass = "Idle" }
   ```

   ОС начнёт отдавать компрессору только свободные ресурсы.

Всё. Флаги — только для дебага/ручной рихтовки, качество подбирается самим инструментом
по каждому файлу.

### Просмотр результатов в Windows (один раз)

Чтобы проводник и «Фото Windows» корректно показывали превью AVIF-картинок и AV1-видео,
один раз поставь системные кодеки-расширения:

```powershell
winget install Microsoft.AV1VideoExtension
winget install Microsoft.HEIFImageExtension
```

На свежих Windows они часто подтягиваются из Store сами; если превью всё равно серые —
добавь ещё `winget install Microsoft.WebPImageExtension`. IrfanView для AVIF требует
свой бесплатный плагин (Formats → avif), Fossify Gallery на Android 12/13+ открывает нативно.

## База данных и зачистка зомби-записей

Идемпотентность держится на `image_compressor.db`: в таблице `processed_images` — строки
по хэшу содержимого (SHA-256): `hash, filename, media_kind, outcome, stamp, achieved,
updated_at`. `outcome=compressed` — «это наш выход, не трогать»; `nochange` + `stamp`
(отпечаток настроек) — «пробовали сжать — не уменьшается, при этих же настройках не
трогать». Старую БД (даже времен Python, где были только `hash+filename`) программа
принимает как есть и молча добавляет свои колонки.

**Быстрый повторный прогон.** Кроме журнала решений, в БД живёт маленькая таблица
`seen(path, size, mtime, hash)` — кэш «путь → хэш содержимого» (ключ — абсолютный путь,
чтобы общая БД на разные корни не путала одноимённые файлы). Если файл лежит там же,
где лежал, и его размер с временем изменения не поменялись, программа не читает его
заново, а берёт хэш из кэша. Для архива на HDD это снимает десятки минут чтения при
каждом повторном запуске: первый прогон читает всё один раз, дальнейшие — только новые
или изменённые файлы. Хэш остаётся единственной истиной: тройка не совпала (файл правили,
вернули из бэкапа, обновили метаданные) — файл честно перечитывается и хэшируется заново.
`--dry-run` кэш не пишет.

**Зомби-записи** — строки, чьего содержимого на диске уже нет (файлы удалили, заменили
извне, вернули оригиналы из бэкапа). В конце **полного успешного** прогона программа
сама удаляет такие строки и дописывает в сводку `Journal pruned: N`. Если прогон был
остановлен, был `--dry-run`/`--fix-ext` или программа шла в `--output` — зачистка не
выполняется. Защита от порчи: если обход увидел меньше половины известного БД (признак
того, что скормили подпапку с общей `--db`), зачистка пропускается с предупреждением.

Практика:

- **Откатил архив к оригиналам из бэкапа?** Ничего делать с БД не нужно: вышедшие из-под
  обхода записи (старые сжатые выходы) первый же полный прогон выметет сам, а оригиналы
  будут сжаты заново честно.
- **Прогон по подпапке с общей БД?** Зачистка сработает только если подпапка покрывает не
  меньше половины записей; иначе она просто пропустится.

## Остановка и продолжение

- **Ctrl+C** — штатная остановка: сразу печатается строка «Stopping: running files finish
  safely, no new files start…», новые файлы не начинаются, текущие кодировки прерываются
  и убирают свои временники, уже заменённые файлы дописываются в БД; в конце — сводка и
  подсказка. Случайно нажал — просто запусти ту же команду снова.
- **Второй Ctrl+C** — немедленный выход. Данные всё равно в безопасности: журнал `staged` +
  атомарные rename, при следующем старте всё дозавершается или откатывается, мусор из
  временников чистится автоматически (`Recover()` + `CleanTemps()`).
- Убийство процесса / ребут / выключение света — тот же механизм, ничего делать руками не нужно.

## Строка статуса и сводка

Живой статус — блок фиксированной высоты: строка счётчиков, строка заголовков
колонок, затем по строке на каждый воркер (всегда их столько, сколько `--workers`).
Слоты **позиционные**: строка N — это воркер N; когда файл закончился, его строка
становится прочёркнутой, следующий файл занимает ту же строку. Ничего никуда не
съезжает и не перезаписывает друг друга, время стоит в ровной колонке, между
временем и путём — колонка прогресса (одинаковая для всех видов файлов):
у видео — ступень CRF с позицией на лестнице и позиция по таймлайну
(«застрял или движется» видно сразу, `crf34 (2/3) 12:31/13:22`),
у фото и анимации — текущая ступень качества (`q85 (1/3)`, у стоп-кадра нет таймлайна),
фаза проверки качества — суффикс `vmaf`, бисекция — `(bis)`;
у всех тяжёлых файлов ожидание свободной дорожки — `queued`. Колонка прогресса не
пустует: фазы вне кодировщика тоже подписаны — `hash` (чтение и SHA-256; для неизменённых
файлов кэш сокращает это до сверки размера и mtime), `still?` (проверка «шляпы» — статичный
кадр с музыкой), `meta` (перенос EXIF/ICC/XMP). На медленном диске это самые долгие
секунды, и раньше они выглядели как зависание. Путь — относительный (с папкой, чтобы было
видно чей файл). ETA из статуса удалён: при порядке «видео последними» байтовая оценка
систематически менялась в разы и только путала.

```
[0:23:11] 19000/46415 (41%)  ok:14000 already:3000 nofit:1500 ext:20 err:3  |  saved 2450 MB
  #  elapsed  stage/position         file
  1       45s  crf28 12:31/13:22     kolya\VID_20260501_120334.mp4
  2        3s  hash                  sveta\dsc_0412.jpg
  3     30:40  crf34 (2/3) 1:16:31/… nina\Video 2020-11-05 14-44-56_join_001_join_002_join_003.avi
  4        1s  q85 (1/3)             hat\music_photo.mp4
  5     12:02  queued                pasha\DSCF0412.MP4
  6      2:11  q85 vmaf              memes\big_animation.gif
...
 12       --                        ← пустой слот прочёркнут
```

Ошибки в консоль живым блоком не пишутся вовсе: растёт только счётчик `err`, а
полный текст каждой ошибки — в `image_compressor.log` (путь печатается при старте).
Считается, что юзер заглянет в журнал, а дёрганье строк на экране ему только мешает.
Если вывод перенаправлен в файл/pipe (не терминал) — вместо блока обычные строки
каждые 1000 файлов, и там ошибки печатаются как есть.

| поле          | что значит                                                                                                                                                                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[0:23:11]`   | время с старта прогона, чч:мм:сс                                                                                                                                                                                                                                     |
| `19000/46415` | файлов обработано / файлов найдено при старте. Знаменатель — ВСЕ файлы дерева: медиа, не-медиа (документы, архивы и т.п.) и уже готовые с прошлых прогонов. Из счёта исключены только наши временники, база и лог                                                    |
| `(41%)`       | то же в процентах. Процент УСЕКАЕТСЯ, а не округляется: 46422/46423 покажет 99%, а не честное 100%, пока воркеры ещё что-то кодят. 100% появляется ровно когда обработан последний файл                                                                              |
| `ok`          | сжато и заменено. Ровно эти файлы и только они формируют `saved`                                                                                                                                                                                                     |
| `already`     | хэш уже есть в БД — файл не тронут. Сюда попадают: сжатые нами ранее, выходы старого Python-компрессора, файлы, которые мы уже пробовали и не сумели уменьшить при текущих настройках, и файлы, перепроверенные при смене настроек и снова не сжавшиеся (подтверждение старого решения — не новый вердикт)                |
| `nofit`       | **новый** вердикт этого прогона: файл прогнали через все честные варианты качества — уменьшить не удалось, оригинал оставлен как есть. Повторные подтверждения старых записей `nochange` живут в `already`                                                                                                          |
| `ext`         | расширение врало содержимому (например .jpg внутри — на самом деле WebP) — починено переименованием. Счётчик пересекает остальные категории: файл может быть посчитан и в `nofit`, и в `ext` одновременно                                                            |
| `err`         | что-то пошло не так: файл не читается, кодировщик упал, ошибка переноса метаданных или записи. Файл при этом не тронут, ошибка попадёт в `image_compressor.log` и будет опробована следующим прогоном. В живом блоке — только счётчик, в pipe-выводе — ещё и строкой |
| `saved`       | МБ, сэкономленные ЗА ЭТОТ прогон: сумма по файлам из `ok` (размер до − размер после). Экономия прошлых прогонов сюда не входит — те файлы сидят в `already`                                                                                                          |

В строках воркеров первым стоит время (фиксированная колонка — оно ровное), потом
путь; имена не обрезаются, кроме случаев когда строка физически не влезает в
ширину консоли — тогда хвост заменяется на `...` (перенос строки сломал бы отрисовку).
Чем файл стал и сколько занял — всегда видно в журнале (`Seconds`).

ETA из свода вычеркнут намеренно: при порядке «тяжёлые видео последними» байтовая
оценка переписывалась вверх в разы на каждой видео-кодировке и только сбивала с толку.
Счётчики и `saved` говорят правду; сколько осталось — видно по `done/total`.
В конце прогона итоговая сводка печатается **под живым блоком**, а не вместо него:
последние рабочие строки остаются видимыми.

`ok + already + nofit + err + non-media` — это и есть счётчик слева: каждый прогнанный файл
попадает ровно в одну корзину, и только `ext` считает поверх неё (файл мог быть и в `nofit`,
и в `ext`). Файлы, которые даже не начали обрабатываться из-за остановки, ни в одну корзину
не попадают.

Итоговая сводка — те же счётчики словами (пример согласован со строкой статуса выше):

```
Done. Compressed: 14000, already processed: 3000, not smaller: 1500, extensions fixed: 20, non-media: 500, errors: 0
Size: 8120.50 MB -> 5610.20 MB = 30.91% saved
Journal pruned: 12 stale entries
```

Эта же сводка одной строкой (`summary`) пишется в `image_compressor.log` — если окно
консоли всё же закроется, итоги прогона останутся в журнале. После полного прогона в
настоящей консоли программа ждёт нажатия Enter; случайно набитые за часы прогона клавиши
сбрасываются, так что окно не закроется само, пока не нажмёшь Enter осознанно.

`Journal pruned: N` появляется только когда полный прогон зачистил зомби-записи БД (см.
раздел про базу данных). Если зачистка сработала на защите «увидено меньше половины БД»,
вместо числа будет предупреждение, и удалено будет 0.

`non-media` — файлы, опознанные по магическим байтам как не фото/видео. В `--output`
режиме они просто зеркально копируются, в in-place не трогаются вовсе.

Строка `Size: A -> B` считает медиа, прошедшие через проверку ЗА ЭТОТ прогон: заменённые
файлы показывают размер до и после, а `already`-файлы — свой текущий размер в обе стороны
(их прошлая экономия в проценты не попадает). Поэтому процент сводки — это экономия
прогона, а не всего архива за всю историю; статусный `saved` с ней совпадает по смыслу.

## Журнал image_compressor.log

Пишется рядом с БД, обычный текст, колонки через таб, UTF-8 с BOM. Размеры — в
мегабайтах, `Seconds` — сколько файл обрабатывался. Каждое изменение — строка:

```
Date	Action	Source	Result	SrcMB	DstMB	SavedMB	Seconds	Kind	Format	Quality	Comment
2026-11-05 02:55:57	compressed	svid.mp4	svid.mp4	0.027	0.026	0.001	8.5	video	mp4	svt p8 crf=34 vmaf=97.2	svt crf28 nofit 3.9s; svt crf34 kept 4.2s; vmaf=97.2 guard 0.4s
2026-11-05 02:55:56	compressed	img.jpg	img.avif	0.014	0.005	0.009	0.4	image	avif	avifenc s6 q=85	avifenc q85 kept 0.4s
2026-11-05 02:55:56	not smaller	liar.jpg	liar.jpg	0.000	0.000	0.000	1.2	image	avif		avifenc q85 nofit 0.4s; avifenc q79 nofit 0.4s; avifenc q73 nofit 0.4s
2026-11-05 02:55:56	ext renamed	liar.jpg	liar.webp	0.000	0.000	0.000	0.0	image	.webp
```

Каждый новый прогон начинается в журнале с пустой строки-разделителя и свежего
заголовка — сразу видно, где закончился один прогон и начался другой (и старый
журнал, начатый байтовыми версиями, не путает: над мегабайтными строками свой
заголовок).

Действия: `compressed` (сжат), `still collapsed` (видео-шляпа схлопнута в фото, см. раздел
«Шляпы»), `not smaller` (не уменьшился — не тронут), `ext renamed`
(исправлено расширение), `error` (все ошибки дублируются сюда). Строка flush'ится сразу —
журнал выживает даже после жёсткого убийства процесса.

## База данных

Тот же файл `image_compressor.db` (SQLite), что и у Python-версии, таблица
`processed_images`. Go бесследно добавляет свои колонки; колонка `achieved` = фактическое
качество результата вместе с победившим энкодером и маркером «как гнали»
(`avifenc s6 q=85`, `svt p8 crf=34 vmaf=96.4` — у SVT виден пресет, у avifenc скорость;
lossless-файлы пишутся словом `lossless`, а не числом) — всегда видно, на каком качестве
и чем файл уже лежит. Правило неизменное: **хэш содержимого
файла в БД → файл никогда не трогается повторно.** Чтобы повторный прогон не читал
архив целиком, тот же хэш кэшируется по тройке `(путь, размер, mtime)`; изменилась
тройка — файл перечитывается и решает уже настоящий SHA-256 (см. «База данных и
зачистка зомби-записей»).

## Как подбирается качество (без ручных прогонов)

- **Фото:** AVIF. Ступени `q 85 → 79 → 73` (пол 61): первая ступень, давшая файл меньше
  оригинала, и есть победа; ниже не идём без нужды. Победитель пониженной ступени
  проверяется libvmaf против оригинала: VMAF ≥ 95 («отличие не видно глазу»), иначе
  бисекция ≤4 проб за точкой «меньше и невидимо»; нет такой — файл не трогается.
  Замерено на архиве: камерные jpg выигрывают уже на базе (−49%); мессенджерные фото
  часто не выигрывают ни на одной ступени (пережатый JPEG дешевле честного AVIF) —
  они остаются как есть, это нормальная работа правила «меньше — или не трогаем».
- **Видео:** MP4+AV1, `crf 28 → 34 → 40` (потолок 45), та же схема «первый уменьшившийся
  уровень побеждает» + libvmaf-guard для повышенных ступеней. Аудио копируется без потерь
  (фолбек на AAC только если контейнер не даёт copy). Принимаются контейнеры mp4/mov/mkv/
  webm/avi (любой опознан по магическим байтам; на выходе всегда честный mp4). Экзотические
  цветовые метки (gbr — запись экрана) AV1-кодировщики отказываются запускать; для таких
  файлов есть последний фолбек с честной конверсией в bt709 — раньше они падали ошибкой,
  теперь либо жмутся, либо честно остаются как есть. Если же не запустился вообще ни один
  энкодер (запись экрана с абсурдным объявленным FPS — SVT отказывает ещё на старте),
  включается **страховка**: тот же подбор прогоняется на аппаратных AV1-энкодерах,
  реально имеющихся на машине (nvenc/amf/qsv). На замере такой битый файл nvenc сжал в
  10 раз быстрее libaom и в 6 раз меньше. `libaom` в страховку не входит — он только по
  флагу `--max` (замер: в ~24 раза дольше SVT при том же crf).
- Итоговое качество каждого файла — в БД (`achieved`) и в журнале.

## Шляпы: статичная картинка с прилепленной музыкой

Много «видео» из соцсетей устроены как один статичный кадр + музыкальная дорожка.
Это фото, переодевшееся в видео: весь вес — музыка и видеонаворот. Программа находит
такие файлы и превращает их в одну фотографию AVIF: сохраняется кадр из середины видео,
музыка выбрасывается. Действие в журнале — `still collapsed`, метка в БД `still q=...`.

Детект — две независимые проверки, обе обязаны пройти:

1. **Смотритель по пакетам** (миллисекунды, читает весь файл без декодирования): в
   неподвижной картинке после первого кадра передавать нечего — пакеты по сотни байт.
   Любое настоящее движение где угодно в файле даёт килобайты. Порог: пакет ≥ 12 КБ —
   значит движение было, это настоящее видео, не трогаем.
2. **Пиксельная верификация кандидата**: все кадры сравниваются друг с другом и с первым
   (128×128 grayscale, средняя разница ≤ 6). Смена кадра (слайдшоу) ловится соседними
   сравнениями, медленный зум — сравнением с первым кадром.

Мелкий анимированный стикер или меняющаяся текстовая плашка поверх статики (примерно до
15–20% кадра) под пороги не попадает и съедается сознательно — кадр сохраняется без неё.
Настоящие видео защищены тем, что на всём таймлайне нет ни одного «жирного» пакета.
Сомнительное всегда уходит по обычной видео-лестнице.

Хочешь посмотреть, что попадёт под схлопывание, без изменений — гоняй `--dry-run`: для
шляп он пишет `-> имя.avif, collapse still-image video to photo`.
Полностью отключить режим: `--no-still`.

## CPU и GPU

- **Фото жмутся на CPU** — так устроен мир AVIF: кодировщики стоп-кадров (avifenc/SVT-AV1)
  программные, GPU-кодирование AVIF в ffmpeg не существует. GPU в фото-фазе не участвует,
  это нормально.
- **Видео по умолчанию жмутся на CPU** (`libsvtav1`) — режим auto не трогает GPU вообще.
  Это боевой канон, установленный после замера на архиве: crf/cq-шкалы у энкодеров разные,
  base-ступень принимается без VMAF-замера, и «победа» быстрого GPU-энкодера обходится
  в 10–25% лишнего размера при непредсказуемом качестве базовой ступени — а если GPU
  не смог уменьшить, за тот же файл всё равно платит SVT. Аппаратные энкодеры — только
  по явному флагу `--gpu` (быстрее, файлы крупнее) или `--max` (libaom, чуть лучше
  качеством, в разы медленнее). Единственное исключение, где GPU включается сам, —
   страховка для файлов, где не запустился вообще ни один энкодер (см. «Как подбирается
   качество»): вызволить файл, который иначе упал бы ошибкой, — другая задача.
   При старте программа **реально проверяет** каждый
  AV1-энкодер микро-кодированием (2 кадра) — в цепочку попадают только живые; если
  SVT-AV1 в ffmpeg нет (essentials-сборка), auto честно деградирует до `libaom-av1`.
- **Какой энкодер реально сжал каждый файл** — пишется в БД (`achieved`) и в журнал
  (колонка Quality: `svt p8 crf=28`, `avifenc s6 q=85`). Шкалы crf между энкодерами не
  сравниваются — запись за тем, чтобы это было видно.
- **Длительность каждой кодировки и guard-проверки** файла пишется в колонку `Comment`
  журнала: `svt crf28 nofit 1180.2s; svt crf34 kept 1350.4s; vmaf=97.1 guard 210.3s` —
  вопрос «почему файл пилился полчаса» отвечает лог, без повторных прогонов. Сумма
  строк Comment и есть время файла: несколько полных прогонов лестницы + guard —
  нормальная цена идемпотентного подбора качества.
- **Ядра делятся автоматически**: фото-стоп-кадрам (avifenc, libvmaf) выдаётся срез
  «ядра ÷ воркеры» (avifenc `-j`, libvmaf `n_threads=`) — их кодировка занимает доли
  секунды и делению не мешает. **Видео и большая анимация работают по-другому**:
  многосекундные AV1-прогоны идут по «дорожкам» — одновременно кодируется
  `ядра ÷ 8` файлов (на 24 потоках — 3), каждому выдаётся жирный срез
  «ядра ÷ дорожки» (lp=8). Причина: SVT-AV1 на lp=2 не разворачивается (бой на
  архиве: 55% загрузки CPU и 40-минутные файлы), а большой gif на `-j2` гниёт ровно
  так же — это такой же многокадровый AV1. Очередь на дорожку видна в статусе
  (`queued`), тяжёлые файлы в списке обхода идут после фото, чтобы дешёвая работа
  не простаивала. Крутить: `--workers` (воркеры) и `--video-workers` (дорожки,
  по умолчанию ядра÷8). На результат кодирования делёж не влияет
  (энкодеры потоково-детерминированы), поэтому в «отпечаток настроек» БД не входит.
- **Весь AV1-видео пишется 10-битным** (`yuv420p10le`): точнее внутренняя арифметика
  кодека, меньше бандинга на градиентах и в тенях, файлы чуть меньше. Проигрыватели
  (Windows/Fossify Gallery) 10-битный AV1 тянут на всём железе с ~2018 года. Пресет
  SVT-AV1 крутится флагом `--video-preset` (8 = канон «баланс»; ниже = чуть меньше
  файлы в разы дольше — имеет смысл только когда скорость не важна).
- Для архива ~100 ГБ на RTX 4080 реалистичный суммарный прогон — единицы-десятки часов.

## Гарантии

- **Никогда не пережимает уже ужатое** (SHA-256 + БД `image_compressor.db`).
- **Меньше — или не трогаем** (файл не заменяется, если не стало реально меньше).
- **Никогда не ухудшает заметно**: ступени, отклонившиеся от базы (вниз у фото, вверх у
  видео), проверяются VMAF против оригинала (порог 95); не прошла — файл остаётся как есть.
- **Не теряет оригинал при падении**: temp → fsync → журнал `staged` → атомарный rename →
  COMMIT в БД; при следующем старте `Recover()` + `CleanTemps()` доводят/откатывают/выметают.
- **Метаданные (EXIF/ICC/XMP) и время файлов переносятся 1-в-1**, GPS/приватность не трогается.
  Если перенести теги не удалось (например exiftool споткнулся), файл НЕ заменяется:
  оригинал остаётся целым, ошибка видна в `err`, а на следующем прогоне файл попробуется снова.
- **Честные расширения**: тип определяется по магическим байтам; враньё в расширении
  чинится всегда, даже если файл не сжимался; цепочки/дубли (`x.mp4.mov`, `x.mp4.mp4`)
  схлопываются в одно честное.

## Сборка

```powershell
go generate ./cmd/ImageCompressor                     # иконка/версия в ресурс
go build -trimpath -ldflags "-s -w" -o dist/image_compressor.exe ./cmd/ImageCompressor
```

Требования: Go, `CGO_ENABLED=0`; бинарники помощников (`avifenc`, `exiftool`, `ffmpeg`
full_build) должны лежать в `internal/assets/tools/windows/` до сборки — они встраиваются
в exe (где взять — в `AGENTS.md`). Кросс-сборка на Linux из Windows работает за счёт
чистого Go (modernc.org/sqlite, без cgo). Архитектура и решения — в `AGENTS.md`, там же
правила для агентов.
