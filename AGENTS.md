Проект: **переписывание ImageCompressor с Python на Go** (семейный фото/видео архив
сжимается до целевого размера/формата; идемпотентно, отказоустойчиво, кросс-платформенно).
Переписывание завершено; PLAN.md выполнен свою роль и удалён. **Источник истины по
архитектуре и решениям — этот файл.** Если решение противоречит ему, сначала обнови
его, потом код.

## Контекст цели (не терять)

- Цель — **максимально сжать медиа без видимых потерь и без потери метаданных/времени**,
  идемпотентно (повтор не трогает готовое) и безопасно (крах не портит данные).
- Это **семейный архив людей**: только фото + видео (+ изредка GIF). Иконок/графики нет.
- Формат обязан **открываться вьюерами** (IrfanView/Windows, Fossify Gallery/Android).
  Была травма: WebP сохранили под именем .jpg → вьюеры ломались. Не повторяем.

## Неизменные правила (критично, данные чувствительные)

1. **Входной тип — только по магическим байтам** (`internal/detect`), расширение не доверять.
   Выход — всегда настоящий формат + честное расширение. Если расширение врёт у файла, который
   мы НЕ меняем (не сжалось/уже обработан) — чинить ВСЕГДА (`ensureHonestExt`: rename; если
   честное имя занято чужим файлом — честное имя с номером `X (2).ext`, враньё чинится всё
   равно, никто не перетирается).
   **ISO-BMFF семейство — одно честное имя:** `.mp4/.mov/.m4v` для `FmtMP4`/`FmtMOV` не считаются
   враньем (`isoFamilyExts`). Без этого правила `ensureHonestExt` переименовывал QuickTime-байты
   в `.mov`, а цель свопа для видео жёстко `.mp4` — и один и тот же бинарник гонял имя туда-сюда
   каждый прогон (боевой пинг-понг шести файлов `other\` в FData).
2. **Никогда не пережимать уже ужатое.** Если SHA-256 содержимого файла есть в БД как
   «processed» → файл не трогать. Это основа идемпотентности (наследие Python-SQLite).
   Повторный прогон не перечитывает гигабайты: таблица `seen(path, size, mtime, hash)` —
   кэш «абсолютный путь → хэш» под тройку `(размер, mtime)`. Совпала тройка — файл не
   читается, хэш берётся из кэша; не совпала (правка/восстановление/чужой touch) — честный
   SHA-256. Истина по-прежнему только `processed_images`: кэш экономит чтение, но не
   подменяет решение. В `--dry-run` `seen` НЕ пишется. **Штамп `nochange` обязан равняться
   `stampFor` от kind, который посчитает детект по байтам:** сравнение идемпотентности в
   `process()` спрашивает `stampFor(res.Kind)` у байт-детекта, и если ветка («шляпа» → `image`)
   перезаписала kind и под него же записала штамп — строка не совпадёт НИКОГДА, файл пережимается
   каждым прогоном (боевой цикл `azart_zay\azart_zay-20230407-0001.mp4` в каждом разделе журнала).
   В `encodeSwap` поэтому держим `origKind` до перезаписи и оба `MarkNoChange` пишем по нему.
   Хэш читается буфером 1 МиБ
   (`io.CopyBuffer`), а не 32 КБ `io.Copy`: на HDD архива мелкий буфер давал seek-thrash
   (~22 МБ/с на 12 хэшеров).
3. **Никогда не удалять/перетирать оригинал до успеха.** Схема: кодировщик пишет в соседний
   temp → `fsync` → журнал `staged` BEGIN → **атомарный rename** → DB COMMIT (одной транзакцией).
   Все файловые операции — только через `internal/safefs`.
   **Имя цели резервируется ДО кодирования** (`claimTarget`, guard после боевой потери **274
   файлов** в FData): честное имя (`X.avif`) могут хотеть два разных источника (`X.jpg`+`X.webp`
   — копии, `X.jpg`+`X.PNG` при регистронезависимой ФС, «шляпа» `X.mp4` рядом с фото `X.jpg`).
   `AtomicReplace` перетирает цель безоговорочно, поэтому если честное имя занято чужим файлом
   или другим воркером прямо сейчас — берётся **имя с номером** (`X (2).avif`, `X (3).avif`,
   потолок `maxNameAttempts`): жмутся оба источника, никто никого не перетирает. Прежний
   «отказаться и не трогать» вариант надолго оставлял такие файлы несжатыми, поэтому теперь имя
   находится всегда; такой своп помечен в Comment журнала `name taken: <имя> owned by another
   file;`. Тот же reserve в `ensureHonestExt` и `fixExtOnly` (чинит враньё в расширении номерным
   честным именем); в `Recover` прерванный свап с чужим содержимым на имени НЕ дописывается —
   источник цел, следующий прогон сожмёт под номерным именем (иначе был бы дубль байт-в-байт).
   **Пути сравниваем так, как их сравнивает ФС** (`samePath`): на Windows `X.MP4` и `X.mp4` —
   ОДИН файл. Считать их двумя → потерять собственный свежий выход: rename на месте, потом
   `RemoveIfExists(«старое» имя)` съедал результат (боевые четыре файла `.MP4` в FData).
4. **Меньше — или не трогаем.** Если результат не меньше оригинала — откат temp, не заменяем.
   Подбор качества — внутри инструмента (CRF-лестница + libvmaf-guard ≥95 с бисекцией):
   эскалированный уровень, давший «заметно хуже оригинала», не принимается никогда.
5. **Метаданные (EXIF/ICC/XMP) и fs-время — переносить как в оригинале.** Приватность/GPS НЕ трогать.
   Перенос тегов НЕ удался (реальная ошибка exiftool) → свап ОТМЕНЯЕТСЯ: temp удаляется,
   оригинал цел, ошибка в `err`, файл ретраится следующим прогоном (не попадает в БД).
   Unicode-пути: exiftool принимает пути ТОЛЬКО через UTF-8 argfile (`-@ -` из stdin) +
   `-charset filename=UTF8`, по одному RAW-аргументу на строку (argfile не разбирает кавычки/
   экранирования); через argv пути с кириллицей/эмодзи всегда калечатся кодовой страницей.

## Стек и кросс-платформ

- Go, **`CGO_ENABLED=0`** (обязательно — иначе ломается кросс-сборка). Один статический бинарник.
- Модуль: `github.com/Llloooggg/ImageCompressor`.
- Зависимости: `modernc.org/sqlite` (чистый Go!), `github.com/h2non/filetype`, `golang.org/x/sync/errgroup`.
  **Не тянуть cgo-зависимости** (mattn/go-sqlite3, libvips и т.п.) — сломают `GOOS=linux` с Windows.
- Кодеки — **внешние бинарники**, не библиотеки внутри Go: `ffmpeg`/`ffprobe`, `exiftool`, `avifenc`
  (fallback на ffmpeg для AVIF). Искать в PATH / рядом с бинарником (`internal/tools`). Не «изобретать»
  AV1/AVIF на чистом Go.
- Платформенно-зависимое (fsync каталога) — через build tags (`//go:build unix` / `//go:build !unix`).

## Внешние утилиты: ВСТРАИВАТЬ в exe (не заставлять юзера ставить)

По правилам проекта помощники-кодеки **пекутся в exe** (как оригинал `--add-binary tools/*.exe`), через
`go:embed all:internal/assets/tools/windows` + распаковку дерева в temp при старте (аналог `_MEIPASS`).
`Locator` ищет: `tools/` у exe → `bin/` → каталог exe → `tools/` cwd → **встроенный temp** → `PATH`.

- **`avifenc`** (статический, официальный AOMediaCodec/libavif) — **встроен**. Фото/анимация самодостаточны.
- **`exiftool`** (exe + дерево `exiftool_files/` с Perl) — **встроен** (структура дерева обязательна!).
- **`ffmpeg`** (видео/AV1) — **встроен** (gyan.dev **full_build**, статика ~228 МБ; `libsvtav1` +
  `libaom-av1` + GPU-AV1; exe ~300 МБ). **`ffprobe` не нужен**: код его не вызывает (роль играют
  `-map 0:a?` + фолбек `-c:a aac`) — не встраивать и не резолвить. Цепочка AV1 строится по
  **реальному пробену** (`ProbeAV1Encoders`: 2 синтетических кадра на каждый энкодер при старте;
  числиться в `-encoders` мало — нужно живое железо), плюс честная деградация svt→aom (`TestBuildVideoChain`).
- Бинарники в `internal/assets/tools/windows/` **не коммитить** (gitignore), но они должны лежать на
  диске перед `go build`, иначе не встраиваются. Скачивать: avifenc — GitHub Releases AOMediaCodec/libavif
  (`windows-artifacts.zip`, статический); exiftool — SourceForge (BITS/`Start-BitsTransfer` обходит JS-заглушку;
  обычный curl/winget упирается в interstitial); ffmpeg full — gyan.dev `ffmpeg-release-full.zip`, либо
  локально из winget-пакета `Gyan.FFmpeg` (`%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg_*\ffmpeg-*-full_build\bin\ffmpeg.exe`).

## Форматы (окончательно)

- Фото → **AVIF** (визуально-lossless). JPEG XL НЕ использовать (плохо открывается вьюерами).
  Качество подбирает сам инструмент, как у видео: лестница q (база 85 → −6 → −12, floor 61) +
  libvmaf-guard (победитель эскалации: VMAF ≥ `--photo-vmaf-min` 95 против оригинала, иначе
  бисекция; нет точки «меньше и невидимо» — не трогаем).
- Видео → **MP4 + AV1**: дефолтная цепочка auto — **только CPU**: `libsvtav1` (честная
  деградация в `libaom-av1`, если в ffmpeg нет SVT). GPU `av1_nvenc/amf/qsv` — **только по
  явным флагам** (`--gpu`, одиночные), `--max`→libaom. Бой зафиксирован в каноне:
  GPU-первый в auto терял и размер, и качество (crf/cq-шкалы не совпадают между энкодерами,
  base-ступень не проверяется VMAF, «не уменьшил» на GPU всё равно оплачивается SVT-прогодом) —
  в auto GPU не возвращать без нового замера; код BuildVideoChain обязан совпадать с этим
  абзацем (однажды разъехался — из-за этого и теряли). Аудио `-c:a copy`;
  `-movflags +faststart`; `-map_metadata 0`. Весь AV1-выход **10-бит** —
  `-pix_fmt yuv420p10le` форсируется всем энкодерам (канон: точнее внутренняя арифметика,
  меньше бандинга; `ProbeAV1Encoders` пробенит тем же пиксельным форматом — железо без
  10-битного AV1-кодирования в цепочку не попадёт). Пресет SVT — дефолт 8 (`--video-preset`,
  ниже = умнее/медленнее; входит в отпечаток настроек). Качество подбирает сам инструмент: CRF-лестница
  (база 28 → +6 → +12, cap 45) + libvmaf-guard (победитель эскалации обязан иметь VMAF ≥95
  против оригинала, иначе бисекция; нет точки «меньше и невидимо» — не трогаем). Входные
  контейнеры: mp4/mov/mkv/webm/**avi** (детект строго по магическим байтам, выход всегда
  честный mp4). Экзотические цветовые метки (gbr/RGB-матрица с экранной записи) заставляют
  AV1-энкодеры **отказываться стартовать** (ffmpeg -22, 0 кадров): `EncodeVideo` имеет
  последний (3-й) фолбек-проход с честной конверсией `-vf scale=out_color_matrix=bt709
  -colorspace bt709 -color_primaries bt709 -color_trc bt709`. Он запускается только когда
  обычный проход дал «ни один энкодер не запустил» — файлы, что иначе упали бы ошибкой.
   **Pass 5 (rescue, канон решения юзера)**: если и после этого ни один энкодер не запустил —
   типичная причина VFR-записи экрана с абсурдным tbr («90k tbr» → SVT отказывает инитом
   «maximum allowed frame rate is 240 fps») — включают **GPU-страховку**: прогон лестницы по
   аппаратным AV1-энкодерам, прошедшим живой пробен, порядок nvenc → amf → qsv (замер на
   реальном битом файле: nvenc в 10 раз быстрее libaom и в 6 раз меньше на экранном контенте).
   **libaom в rescue НЕ ходит** — «libaom только флагом» (замер: cu8 в ~24 раза дольше SVT p8
   при том же crf; авто никогда не вызволит 24×-медленный CPU-прогон). Нет GPU-AV1 на машине —
   файл честно остаётся в `err` и ретраится следующим прогоном.
- Анимация (gif/аним.webp) → **аним. AVIF** (решено: ок, avifenc с native-чтением GIF, фолбек ffmpeg).
- «Шляпы» (соцсети: один статичный кадр + прилепленная музыка) → **схлопывать в одну AVIF-фото**
  (аудио выбрасывается — решение юзера, «музыка в таких шляпах не нужна»). Детект
  `internal/media/still.go`: смотритель по пакетам — чистый Go парсер MP4/MOV (stsz/stss,
  **ffprobe не используем**), любой inter-пакет ≥12 КБ = движение где-то было → не шляпа; кандидат
  проходит пиксельную верификацию ffmpeg (все кадры 128×128 gray, MAD ≤ 6 против соседнего И
  первого — слайдшоу и Ken Burns ловятся). Мелкие стикеры/плашки поверх статики (~до 20% кадра)
  съедаются сознательно (решение юзера), всё сомнительное — на общую лестницу. По умолчанию
  включено, отключение `--no-still`; achieved-метка `still q=85`, действие журнала `still collapsed`.
  **«Шляпа» НЕ схлопывается, если в той же папке уже есть файл с тем же стемом** (`stemTwins` —
  карта «кто ещё хочет это имя», строится в `gather` через `stemKey`/`countStem`; вопрос в `process`
  через `hasStemTwin`): фото `X.jpg` рядом с клипом `X.mp4` УЖЕ хранит эту картинку, а кадр из
  клипа хотел бы имя `X.avif` — именно так 160 боевых фото из 274 потерянных файлов были заменены
  выдернутым кадром. Счёт ведём по ИМЕНИ (расширение = потенциальный претендент на выход,
  не-медиа-соседи вроде `X.txt` не считаются), тип файла по-прежнему только по магическим байтам
  (как `videosLast`). Такой клип идёт обычную видео-лестницу (или остаётся как есть).

## Стиль

- **Весь текст программы (интерфейс, ошибки, журнал) — только английский**; никаких
  декоративных скобок в выводах; в статусе нет МБ/с (метрика удалена по требованию юзера).
- Идиоматичный Go: `context.Context` на всех долгих операциях и внешних процессах;
  параллелим `errgroup.SetLimit(workers)`; ошибки оборачивать `fmt.Errorf("...: %w", err)`;
  `database/sql` + `modernc.org/sqlite`.
- Конфиг/флаги: `--input --output --gpu --max --photo-q --photo-vmaf-min
  --photo-speed --photo-lossless --video-crf --video-vmaf-min --video-workers --video-preset
  --workers --no-still --fix-ext --dry-run --yes`.
  **Дефолты таковы, что exe без аргументов сжимает
  свою папку рекурсивно** (вход = папка исполняемого файла) — это основной способ эксплуатации
  («кинул экзешник в корень = магия»); флаги — дебаг/ручная рихтовка, не просить юзера гонять
  несколько прогонов с разными crf. Дефолты качества: `--photo-q 85` и `--video-crf 28` (флоры лестниц),
  `--photo-vmaf-min 95`, `--video-vmaf-min 95`, `--photo-speed 6` (канон «сжатие важнее скорости»).
  Параллелизм: `--workers` + **авто-бюджет ядер на дочерний процесс** (`childBudget`),
  не трогать семантику без согласования. **Тяжёлые дорожки (lanes, боевая починка «55% CPU»)**:
  многосекундные AV1-прогоны — ВИДЕО И АНИМАЦИЯ (gif/webp — тоже полноценный многокадровый
  AV1, на `-j2` гниёт минуты) — идут по семафору `vsem`, дефолт дорожек = ядра/8
  (`DefaultVideoLanes`, на 24 потоках = 3), каждому дорожному процессу бюджет =
  ядра/дорожки (lp=8 — на lp=2 SVT не разворачивается); фото-стоп-кадры семафор не ждут,
  живут старым делением (`workers`). `--video-workers` — ручная рихтовка, lanes никогда
  > workers. Тяжёлые файлы в очереди обхода ЕДУТ ПОСЛЕДИ (`videosLast`, по расширению
  включая .gif — порядок-подсказка, ДЕТЕКТ ВСЁ ЕЩЁ только по магическим байтам).
  **Холодное чтение больших файлов (`hsem`, боевая починка «22 МБ/с»)** — отдельный семафор,
  не путать с `vsem`: файлы ≥64 МБ (`bigHashThreshold`) хэшируются не более чем по 3 сразу
  (`bigHashLanes`), мелочь и кэш-хиты `seen` семафор не ждут; дорожка держится ТОЛЬКО на
  время чтения, не на кодирование (разные узкие места); ожидание подписано `hash queued`.
  Замер: 12 параллельных хэшеров на HDD архива давали ~22 МБ/с суммарно (seek-thrash).
  Пресет SVT: `--video-preset` (дефолт 8, канон), входит в видео-отпечаток настроек БД
  (сменил пресет — nofit-файлы пересмотрятся); скорость avifenc `--photo-speed` —
  симметрично входит в фото/anim-отпечаток. Подтверждение перед мутированием (skip `--yes`); пауза в конце в TTY
  (**обязателен сброс буфера консоли `flushStdin` перед чтением**: за часы прогона в stdin
  копятся нерочитанные клавиши/Enter, без сброса окно даблклика закрылось бы мгновенно,
  проглотив мусор, — юзер бы не увидел сводку). Сводка прогона дублируется одной строкой
  `summary` в `image_compressor.log` — переживает закрытие окна.
- UX/учёт: живой статус — БЛОК ФИКСИРОВАННОЙ ВЫСОТЫ (`workers+2` строки: шапка счётчиков
  ok/already/nofit/ext/err + экономия MB; **ETA УДАЛЁН** — врал при videos-last, не возвращать;
  строка заголовков колонок `# elapsed stage/position file`); по строке на каждый воркер —
  ВСЕГДА, слоты **ПОЗИЦИОННЫЕ** (`trackStart` возвращает индекс: строка N это воркер N,
  освободилась — прочёркнута, следующий файл занимает её же; строки никогда не съезжают —
  боевая жалоба «раннер прыгает между строк»); внутри слота СВЕРХУ ВНИЗ: №, время колонкой `%8s` ПЕРЕД
  путём (`fmtDurShort`: <1м `45s`, <1ч `20:30`, дальше `1:30:22` — голые секунды
  нечитабельны), МЕЖДУ временем и путём — колонка прогресса видео `%-21s` (`crf28 4:31/13:22`;
   `-progress pipe:2`/out_time_ms; длительность — заголовки `ffmpeg -i`, ffprobe по-прежнему
   НЕ используем; ожидание тяжёлой дорожки — `queued`; у фото/анимации — текущая ступень
   лестницы (`q85`, `lossless`) без позиции: у стоп-кадра нет таймлайна). Пустой слот
   НЕДОПУСТИМ: фазы вне кодировщика подписаны в той же колонке — `hash` (чтение и SHA-256;
   кэш обычно убирает само чтение), `hash queued` (ожидание дорожки холодного чтения
   большого файла), `still?` (пиксельная проверка «шляпы»), `meta` (перенос
   тегов exiftool); на HDD это десятки секунд-минуты, и без метки выглядит как зависание.
   **позиция ступени
    `(2/3)`** при лестнице >1 ступени (и у видео `crf34 (2/3)`, и у фото `q91 (2/3)`), бисекция
    — `(bis)`, фаза либвмаф-гарда — суффикс ` vmaf` БЕЗ таймлайна (encode окончен, считается
    метрика — боевой случай «зависло на 22:40/22:40» больше не вводит в заблуждение),
    затем относительный путь). Сводка в конце печатается **НИЖЕ блока** (блок не стирается —
    боевая жалоба «done-строка затёрла все предыдущие строки»). Счётчик `nofit` — только
    НОВЫЕ вердикты прогона; если файл уже лежал в БД как `nochange` и при смене штампа
    перепроверился и снова не сжался — это подтверждение старого решения, идёт в `already`
    (флаг `retried` в encodeSwap). Имена НЕ обрезать, кроме превышения ширины
  консоли (`vt.Width`, clip rune-safe — перенос строки ломает курсорную арифметику).
  Проценты УСЕКАТЬ (не округлять): 100% не раньше последнего файла. ОШИБКИ в VT-режиме
  в консоль НЕ печатать вообще (`r.logf` muted,
  `r.multi`=true): только счётчик `err:` + журнал (решение юзера — не дёргать блок). В
  non-VT/pipe режиме ошибки печатать в stderr как раньше. `--dry-run` принудительно
  single-line (`r.multi = tty && !DryRun && vt.Enable`), чтобы `[dry-run]`-строки струились.
  В pipe — строки каждые 1000 файлов. Рендер через VT (`internal/vt`: windows — kernel32
  SetConsoleMode ENABLE_VIRTUAL_TERMINAL_PROCESSING + GetConsoleScreenBufferInfo для
  ширины, !windows — noop/width 0→fallback 100); одиночные сообщения — только через
  `printBreak` (стирает блок целиком по `blockLines()`, печатает строку, следующий repaint
  с `firstDraw`). Одноимённый ярлык в статусе — `already:` (не `done:` — путают с `ok`).
  Рядом с БД пишется `image_compressor.log` (журнал «чем было → чем
  стало → как изменился вес»; размеры в МБ, колонка `Seconds` — время обработки файла;
  НОВЫЙ ПРОГОН = пустая строка-разделитель + свежий хедер над своими строками);
  в БД колонка `achieved` = фактическое качество результата с победившим энкодером
  и маркером «как гнали» (`avifenc s6 q=85`, `svt p8 crf=34 vmaf=96.4` — префикс энкодера
  обязателен, шкалы между энкодерами несравнимы; у SVT пресет `p<N>`, у avifenc скорость
  `s<N>` — оба меняют вес/качество и решают, есть ли смысл перекладывать файл; lossless
  пишется словом `lossless`, число q там вранье; анимация пишет победивший кодировщик
  (`avifenc`/`aom`); 10-бит — константа канона, не пишется); колонка `Comment` журнала — полная летопись попыток файла
  (кодер ступень итог длительность: `svt crf28 nofit 1180.2s; svt crf34 kept 1350.4s;
  vmaf=97.1 guard 210.3s`) — «почему файл пилился полчаса» должно отвечать одно чтение лога);
  `--output` = **полное зеркало** входа (не-медиа тоже копируются). Своп, взявший номерное имя
  (честное занято чужим файлом) помечен в Comment префиксом `name taken: <имя> owned by another
  file;` — отдельного действия журнала для него нет, строка остаётся `compressed`/`ext renamed`
  с фактическим номерным Result-именем;
  отказ «шляпы» уменьшиться помечается в Comment префиксом `hat:`, иначе Kind=`image` в
  журнале читается как будто файл всегда был фото.
- Не переусложнять. Оркестратор, а не реимплементация кодеков.

## Журнал БД и GC зомби-записей

- Схема журнала (после выпиливания легаси): `hash, filename, media_kind, outcome, stamp,
  achieved, updated_at` + `staged` (крах-журнал свапа, живёт секунды) + `seen(path, size,
  mtime, hash)` (кэш перечитывания; см. правило 2).
  Колонок `tool/tool_version/migrated/format` в коде больше нет; в живой БД их сносит
  **одноразовая ручная операция** (helper вне репо: DELETE legacy-строк → DROP COLUMN ×4 →
  VACUUM), код работает и с колонками, и без них.
- `--migrate` и вся легаси-поддержка ВЫПИЛЕНЫ: перепись живой БД доказала, что
  python-контента на диске не осталось (752 «немигрированных» строки — зомби, у
  622 уже есть пара `mediacompressor/compressed`).
- **GC зомби (канон)**: обход наблюдает хэш каждого медиа-файла (`r.observe` + явное
  наблюдение `newHash` после свапа); в конце ПОЛНОГО успешного прогона (не dry-run,
  не fix-ext, не --output, не остановка) `PruneUnseen` удаляет строки ненаблюдённого
  содержимого. Барьер: наблюденных меньше половины строк БД → зачистка пропускается
  (признак подпапки с общей `--db`), в сводке — `Journal pruned: N` или предупреждение.
  Та же зачистка уносит строки `seen`, чей хэш больше не существует в
  `processed_images` (путь описывает мёртвый контент); строки живого контента остаются.
  Бонус: ручная чистка БД перед редо архива больше не нужна — осиротевшие строки
  уезжают сами первым же прогоном.
